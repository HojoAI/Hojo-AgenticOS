# 会议服务声纹识别流程文档

## 一、概述

会议服务在实时会议场景中，对每个音频段进行声纹识别，以识别说话人身份。声纹识别流程包括：
1. 从音频中提取声纹向量
2. 并行匹配正式表和临时表
3. 如果未匹配到，创建新的临时说话人并保存

---

## 二、声纹识别时机

### 2.1 触发时机

声纹识别在以下时机触发：

**音频段完成时**：
- 当ASR（语音识别）完成一个音频段的识别后（`isEnd == 1`）
- 在 `completeCurrentSegment()` 方法中调用
- 对完整的音频段进行声纹识别，而不是对每个音频包

**触发条件**：
```java
if (asrResponse.getIsEnd() == 1) {
    completeCurrentSegment(session, state);
}
```

### 2.2 音频段处理流程

```
音频包接收 → VAD检测 → ASR识别 → ASR完成(isEnd=1) → 声纹识别 → 段完成
```

## 三、声纹识别完整流程

### 3.1 流程图

```
开始
  ↓
调用语音服务提取声纹向量
  ↓
声纹向量是否有效？
  ├─ 否 → 创建兜底临时说话人 → 结束
  └─ 是 → 继续
  ↓
并行匹配（CompletableFuture）
  ├─ 匹配正式表（user_voiceprints）
  └─ 匹配临时表（meeting_voiceprints，按meetingId过滤）
  ↓
等待两个结果
  ↓
正式表是否匹配成功？
  ├─ 是 → 返回正式表用户信息 → 结束
  └─ 否 → 继续
  ↓
临时表是否匹配成功？
  ├─ 是 → 返回临时表说话人信息 → 结束
  └─ 否 → 继续
  ↓
创建新的临时说话人
  ├─ 生成speakerId（UserId-{index}）
  ├─ 生成speakerName（发言人-{index}）
  └─ 保存到临时表
  ↓
返回新说话人信息
  ↓
结束
```

### 3.2 详细步骤

#### 步骤1：提取声纹向量

**方法**: `performVoiceprintRecognition()`

**操作**:
1. 构建声纹识别请求（`VoiceprintRequest`）
2. 生成唯一vid（使用Snowflake）
3. 将音频数据Base64编码
4. 调用语音服务接口：`/v1/voiceprint/recognize`

**代码位置**:
```java
VoiceprintRequest request = new VoiceprintRequest();
String voiceprintVid = String.valueOf(snowflake.nextId());
request.setVid(voiceprintVid);
String audioBase64 = Base64.getEncoder().encodeToString(audioData);
request.setAudioLength(audioBase64.length());
request.setAudio(audioBase64);

VoiceprintResponse response = voiceBaseServiceClient.recognize(request).getResContent();
```

**异常处理**:
- 如果声纹识别失败（`rtn != 0`），返回兜底临时说话人
- 如果声纹向量为空，返回兜底临时说话人

#### 步骤2：并行匹配

**方法**: `performVoiceprintRecognition()` 中的并行匹配逻辑

**并行调用**:
1. **匹配正式表**：调用 `/v0/voiceprint/match`
2. **匹配临时表**：调用 `/v0/voiceprint/match-temporary`

**实现方式**:
```java
CompletableFuture<Response<UserMatchResult>> formalMatchFuture = CompletableFuture.supplyAsync(() -> {
    return storageServiceClient.matchVoiceprint(voiceprintMatchRequest);
});

CompletableFuture<Response<UserMatchResult>> temporaryMatchFuture = CompletableFuture.supplyAsync(() -> {
    return storageServiceClient.matchTemporaryVoiceprint(temporaryRequest);
});
```

**参数说明**:
- `voiceprint`: 声纹向量（192维double数组）
- `threshold`: 相似度阈值（默认0.85，可配置）
- `meetingId`: 会议ID（临时表匹配必需）

**等待结果**:
```java
Response<UserMatchResult> formalResult = formalMatchFuture.get();
Response<UserMatchResult> temporaryResult = temporaryMatchFuture.get();
```

#### 步骤3：结果处理

**优先级规则**:
1. **优先使用正式表结果**：如果正式表匹配成功，直接返回
2. **其次使用临时表结果**：如果正式表未匹配，使用临时表结果
3. **创建新说话人**：如果两个表都未匹配，创建新的临时说话人

**代码逻辑**:
```java
// 优先返回正式表的匹配结果
if (formalResult != null && formalResult.getResContent() != null) {
    UserMatchResult userMatch = formalResult.getResContent();
    // 返回正式表用户信息
    return info;
}

// 如果正式表未匹配到，使用临时表的结果
if (temporaryResult != null && temporaryResult.getResContent() != null) {
    UserMatchResult tempMatch = temporaryResult.getResContent();
    // 返回临时表说话人信息
    return info;
}

// 如果两个表都没有匹配到，创建新的临时说话人
```

#### 步骤4：创建新说话人

**生成规则**:
- `speakerId`: `"UserId-" + speakerIndex`（如：UserId-1, UserId-2）
- `speakerName`: `"发言人-" + speakerIndex`（如：发言人-1, 发言人-2）
- `speakerIndex`: 使用原子计数器递增，确保唯一性

**保存到临时表**:
```java
VoiceprintSaveTemporaryRequest saveRequest = new VoiceprintSaveTemporaryRequest();
saveRequest.setMeetingId(state.meetingId);
saveRequest.setSpeakerId(newSpeakerId);
saveRequest.setSpeakerName(newSpeakerName);
saveRequest.setVoiceprint(voiceprint);
storageServiceClient.saveTemporaryVoiceprint(saveRequest);
```

**注意事项**:
- 保存失败不影响主流程，只记录日志
- 使用 `ON CONFLICT DO NOTHING`，同一说话人多次说话不会覆盖

## 四、异常处理

### 4.1 声纹识别失败

**场景**: 语音服务返回错误或声纹向量为空

**处理**:
- 创建兜底临时说话人（`createFallbackSpeaker()`）
- 说话人ID和名称按规则生成
- **不保存声纹向量**（因为识别失败）

**日志**:
```
[声纹失败] meetingId: {}, vid: {}, rtn: {}, msg: {}, 将使用兜底临时说话人
```

### 4.2 匹配接口异常

**场景**: 匹配正式表或临时表时发生异常

**处理**:
- 捕获异常，记录错误日志
- 返回null，继续后续流程
- 如果两个匹配都失败，创建新说话人

**日志**:
```
[匹配正式表异常] meetingId: {}
[匹配临时表异常] meetingId: {}
```

### 4.3 保存临时声纹失败

**场景**: 保存新说话人到临时表时失败

**处理**:
- 捕获异常，记录错误日志
- **不影响主流程**，仍然返回说话人信息
- 下次匹配时可能无法匹配到该说话人（因为未保存）

**日志**:
```
[保存临时说话人失败] meetingId: {}, speakerId: {}
```

## 五、配置参数

### 5.1 相似度阈值

**配置项**: `voiceprint.similarity.threshold`

**默认值**: `0.85`

**说明**:
- 用于判断声纹匹配是否成功
- 相似度 >= 阈值时，认为匹配成功
- 可在配置文件中修改

**配置位置**: `application.properties`
```properties
voiceprint.similarity.threshold=0.85
```

### 5.2 阈值传递

**正式表匹配**:
- 请求参数：`VoiceprintMatchRequest.threshold`
- 如果不传，使用默认值0.85

**临时表匹配**:
- 请求参数：`VoiceprintMatchTemporaryRequest.threshold`
- 如果不传，使用默认值0.85

## 六、数据清理

### 6.1 清理时机

**会议结束时**：
- 前端发送 `REQ_MEETING_STOP` 事件
- 在 `handleMeetingStop()` 方法中处理
- 完成会议后，调用清理接口

**代码位置**:
```java
private void handleMeetingStop(WebSocketSession session, String message, SessionState state) {
    // ... 完成会议处理 ...
    finishMeeting(session, state, needSave);
    
    // 清理会议临时声纹数据
    try {
        storageServiceClient.deleteTemporaryVoiceprints(state.meetingId);
        logger.info("[清理临时声纹数据] meetingId: {}", state.meetingId);
    } catch (Exception e) {
        logger.error("[清理临时声纹数据失败] meetingId: {}", state.meetingId, e);
    }
}
```

### 6.2 清理接口

**接口**: `DELETE /v0/voiceprint/temporary/{meetingId}`

**功能**: 删除指定会议的所有临时声纹记录

**异常处理**:
- 清理失败不影响主流程，只记录日志
- 避免因清理失败导致会议结束流程中断

## 七、性能优化

### 7.1 并行匹配

**优化点**: 同时匹配正式表和临时表，而不是串行

**优势**:
- 减少总等待时间
- 提升响应速度

**实现**: 使用 `CompletableFuture.supplyAsync()` 并行执行

### 7.2 数据库查询优化

**临时表查询**:
- 使用 `meeting_id` 索引快速定位
- 使用向量索引（如果数据量大）加速相似度计算
- 使用 `LIMIT 1` 只返回最相似的结果

**正式表查询**:
- 使用向量索引加速相似度计算
- 使用 `LIMIT 1` 只返回最相似的结果

## 九、数据流

### 9.1 音频数据流

```
客户端音频包
  ↓
WebSocket接收
  ↓
VAD检测（语音活动检测）
  ↓
ASR识别（语音转文字）
  ↓
ASR完成（isEnd=1）
  ↓
合并音频段
  ↓
声纹识别（提取向量）
  ↓
并行匹配（正式表 + 临时表）
  ↓
返回说话人信息
  ↓
保存段信息（包含说话人）
```

### 9.2 声纹数据流

```
声纹向量提取
  ↓
并行匹配
  ├─ 正式表（user_voiceprints）
  │   └─ 全局已注册用户
  └─ 临时表（meeting_voiceprints）
      └─ 当前会议临时说话人
  ↓
匹配结果
  ├─ 匹配成功 → 返回用户/说话人信息
  └─ 匹配失败 → 创建新说话人 → 保存到临时表
```

## 十、服务依赖

### 10.1 语音服务

**接口**: `POST /omniasst-voice/v1/voiceprint/recognize`

**功能**: 从音频中提取声纹向量

**请求参数**:
- `vid`: 唯一标识
- `audio`: Base64编码的音频数据
- `audioLength`: Base64编码后的长度

**响应**:
- `rtn`: 返回码（0表示成功）
- `voiceprint`: 声纹向量（192维double数组）

### 10.2 管理服务

**接口1**: `POST /omniasst-management/api/v0/voiceprint/match`
- 匹配正式表声纹

**接口2**: `POST /omniasst-management/api/v0/voiceprint/match-temporary`
- 匹配临时表声纹

**接口3**: `POST /omniasst-management/api/v0/voiceprint/save-temporary`
- 保存临时声纹

**接口4**: `DELETE /omniasst-management/api/v0/voiceprint/temporary/{meetingId}`
- 清空会议临时数据

## 十一、注意事项

1. **声纹识别时机**：只在音频段完成时进行，不对每个音频包识别
2. **并行匹配**：正式表和临时表并行匹配，提升性能
3. **优先级**：正式表匹配结果优先于临时表
4. **数据持久化**：临时声纹存储在数据库中，避免内存丢失
5. **数据清理**：会议结束时必须清理临时数据，避免累积
6. **异常处理**：各步骤都有异常处理，确保主流程不中断
7. **阈值配置**：相似度阈值可配置，默认0.85
8. **说话人命名**：临时说话人ID和名称由代码生成，格式固定

## 十二、常见问题

### Q1: 为什么使用并行匹配而不是串行？

**A**: 并行匹配可以减少总等待时间。如果串行匹配，总时间 = 正式表匹配时间 + 临时表匹配时间。并行匹配时，总时间 ≈ max(正式表匹配时间, 临时表匹配时间)。

### Q2: 如果保存临时声纹失败会怎样？

**A**: 保存失败不影响主流程，仍然返回说话人信息。但下次该说话人再次说话时，可能无法匹配到（因为未保存），会创建新的说话人。

### Q3: 同一说话人多次说话会覆盖声纹吗？

**A**: 不会。使用 `ON CONFLICT DO NOTHING`，保留第一次的声纹向量。这样可以确保说话人身份的一致性。

### Q4: 会议结束时清理失败会怎样？

**A**: 清理失败不影响主流程，只记录日志。但会导致临时数据残留，需要定期手动清理或通过定时任务清理。

### Q5: 声纹识别失败时为什么创建兜底说话人？

**A**: 确保每个音频段都有说话人信息，即使声纹识别失败。兜底说话人不保存声纹向量，只用于显示。
