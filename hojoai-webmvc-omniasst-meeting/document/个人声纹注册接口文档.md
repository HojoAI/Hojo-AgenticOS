# 会议场景 · 个人声纹注册接口文档

> **修改昵称**：与阶段二提交**共用同一接口** `POST /omniasst-meeting/v1/meeting/voiceprint/register/commit`，**不**新增 URL；在 JSON Body 中增加 **`"updateNicknameOnly": true`** 即可（见 **§5.5**）。

## 1. 功能说明

会议服务内已实现两阶段注册。multipart `prepare` 与产品约定对齐：`type` 表示 **0=声音（默认）**、**1=声纹**（与 `GET .../voice/profile` 的 `type` 语义对齐）；`needSave` 原样转发 management 克隆。JSON `prepare` 仍用整数 `type` 表示 0=复用已有声纹（无音频）、1 或省略=新录（与 multipart 语义不同）。`replicateType` 仅作用于 JSON `prepare`、`copy-voice` 的校验（勿在 JSON 上误传 `VOICE`，声音场景用 multipart `type=0` 或省略）。**`commit` 不传 `replicateType` / `type`**，走声纹或仅音色保存由阶段一写入 Redis 的暂存决定。

| 方式 | 接口 | 作用 |
|------|------|------|
| 阶段一 | `prepare`（multipart） | **必填** `file`（WAV）、`needSave`、`provider`；`type=0` 或省略 声音：仅克隆，不调声纹抽取；`type=1` 声纹：克隆 + 声纹抽取暂存 |
| 阶段一 | `prepare`（JSON）或 **`copy-voice`** | 新录：`audio`/`audioBase64`；**复用**：JSON 传 **`type=0`** 且无音频，或调 **`POST .../copy-voice`** |
| 阶段二 | `commit` | 填昵称；**声纹**流程调 `voiceprint/register`；**复用 / multipart 声音(type=0 或省略)** 仅 `voice/save`，不调声纹注册 |
| 阶段二 | `commit`（**仅改昵称**） | 传 `updateNicknameOnly=true` 时**不要求**阶段一 Redis 暂存：直接更新 management 音色昵称与声纹表展示名，见 **§5.5** |

依赖：

- Redis：暂存 `pending` 数据  
- Voice 服务（`bypass-voice-recognition=false` 且 `prepare` 为声纹 `type=1` 时）：`POST /omniasst-voice/v1/voiceprint/recognize/file`（`multipart/form-data`，上传 WAV 文件，返回 `resContent.voiceprint` 向量）  
- Management 服务（默认 `commit-skip-management=false`）：
  - 阶段一音色克隆：`POST /omniasst-management/api/v0/voice/clone`（`multipart/form-data`，字段：`userId`、`voiceName`(可选)、`provider`、`needSave`、`file`；WAV；建议 ≤10MB）
  - 阶段二声纹录入：`POST /omniasst-management/api/v0/voiceprint/register`（`multipart/form-data`，字段：`userId`、`userName`、`audioFile`；WAV；建议 ≤10MB）
  - **仅改昵称**（`commit` 且 `updateNicknameOnly=true`，未开启 `commit-skip-management` 时）：
    - `GET /omniasst-management/api/v0/voice/profile`（查询音色 `voiceId`、原 `voiceName`）
    - `POST /omniasst-management/api/v0/voice/save`（更新 `nickname` 等，见《音色管理》侧约定）
    - `POST /omniasst-management/api/v0/voiceprint/display-name`（更新 `user_voiceprints.user_name`；若用户无声纹行则会议侧忽略该步失败，见《声纹管理接口文档》）

## 3. 统一响应结构

与项目内其他接口一致，使用 `Response<T>`（字段名以实际 `hojoai-common` 为准，常见如下）：

| 字段 | 类型 | 说明 |
|------|------|------|
| resCode | String | 多为 `OK`（含业务失败仍返回 HTTP 200 的场景，**须结合 `resMessage` 判断成功/失败**） |
| resMessage | String | 描述信息；成功多为 `SUCCESS`，失败多为约定分支码（如 `SAVE_FAILED`） |
| resContent | T | 业务数据；失败时个人声纹注册路径下常含 **`detail`**（原因说明） |

业务异常可能仍返回 **HTTP 500** 及 Spring 默认 JSON（`timestamp`、`status`、`error`、`path`），请以日志与联调环境为准。

## 4. 接口一：阶段一 prepare

### 4.1 描述

**multipart**：录制结束后调用；**必填** WAV `file`、`needSave`、`provider`。`type=0` 或省略（默认）为 **声音**：仅克隆、**不**调声纹抽取，`commit` 仅 `voice/save` 昵称，**不**调 `voiceprint/register`。`type=1` 为 **声纹**：克隆（`needSave` 转发 management）+ 声纹抽取，暂存向量与音频供 `commit` 调声纹注册。

**复用已有声纹（无新录音）**：请使用 **`POST .../copy-voice`**（JSON），或 **JSON `prepare`** 且 **`type=0`**（不传 `audio`）；**勿**再用 multipart 无 `file` 形式。

**JSON `prepare`**：`type=0` 复用 / `type=1` 或省略 + `audio` 新录；详见下文「请求方式 B」。**`replicateType`** 用于 JSON 路径，与 **multipart 的 `type`（0 声音 / 1 声纹）** 不是同一套语义。

### 4.2 请求方式 A（multipart，与产品字段对齐）

| 项 | 值 |
|----|-----|
| Method | `POST` |
| Path | `/omniasst-meeting/v1/meeting/voiceprint/register/prepare` |
| Content-Type | `multipart/form-data` |

**表单字段：**

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| userId | String | 是 | 当前用户 ID |
| file | File | 是 | WAV 格式音频 |
| needSave | boolean | 是 | 转发 management `clone`：`true` 克隆结果直接入库，`false` 不入库 |
| provider | String | 是 | 厂商：`hojo`（恒聚）、`minimax` 等，与 management 约定一致 |
| voiceName | String | 否 | 音色名称，随 clone 转发 |
| type | Integer | 否 | **`0`** 或省略=声音（默认，仅克隆，阶段二不写声纹库）；**`1`**=声纹 |

**curl 示例（声音，默认不传 type）：**

```bash
curl -X POST "http://{host}:{port}/omniasst-meeting/v1/meeting/voiceprint/register/prepare" \
  -F "userId=user123" \
  -F "provider=hojo" \
  -F "needSave=true" \
  -F "file=@/path/to/audio.wav"
```

**curl 示例（声纹，type=1）：**

```bash
curl -X POST "http://{host}:{port}/omniasst-meeting/v1/meeting/voiceprint/register/prepare" \
  -F "userId=user123" \
  -F "provider=hojo" \
  -F "needSave=false" \
  -F "type=1" \
  -F "file=@/path/to/audio.wav"
```

### 4.3 请求方式 B（JSON，与 multipart 字段不同）

| 项 | 值 |
|----|-----|
| Content-Type | `application/json` |

**Body：** `userId`；新录时 `audio` 或 `audioBase64`（WAV 转 Base64）；**复用**时 **`type=0`** 且不要带音频；可选 `provider`、`replicateType`。此路径下整数 **`type` 仍为 0=复用 / 1 或省略=新录**，**不是** multipart 的「0 声音 / 1 声纹」。声音-only 场景请用 **multipart `type=0` 或省略**。

### 4.4 响应

与项目统一 **`Response<T>`**：`resCode`、`resMessage` 等见公共约定；**`resContent` 为 JSON 对象**（业务体，非字符串），字段如下。

**成功时 `resContent`：**

| 字段 | 类型 | 说明 |
|------|------|------|
| voiceId | String \| null | 音色 ID（management `clone` / 复用 profile）；与 `voice_id` 同义；**成功路径应有值**（联调 `bypass` 等例外见下） |
| cloneVoiceId | String | 可选；仅当 `remote-prepare-enabled=true` 且 management prepare 返回时有值 |

暂存在 Redis 中按 **`userId` 唯一定位**（键形如 `meeting:vp:reg:pending:user:{userId}`），TTL 见配置（默认 30 分钟）。**同一用户再次 `prepare` 会覆盖**上一份暂存。

**与前端约定的分支码（读外层 `resMessage`）：**

- **成功：** `resCode` 多为 `OK`，`resMessage` 为 **`SUCCESS`**。

**失败时（录音检测、复用校验等）：** HTTP 仍为 **200**，`resCode` 多为 `OK`，**`resMessage` 仅为下表之一**。`resContent` 中可能带有 **`detail`**（字符串，服务端异常说明），供联调与排障；**前端弹窗仍以 `resMessage` 分支为主**，可忽略 `detail`。

| resMessage | 场景 |
|------------|------|
| `GENERIC_ERROR` | prepare 阶段通用失败（参数/服务不可用/克隆失败/抽取失败且文案未判为嘈杂等） |
| `NOISY_ENVIRONMENT` | prepare 阶段声纹服务返回的失败文案命中「嘈杂、噪、信噪、noise、SNR」等启发式规则时 |

### 4.5 说明

- 阶段二 `commit` 的 `userId` 须与阶段一 **一致**，用于读取该用户的暂存。  
- **阶段二依赖阶段一写入的音频**；Redis 过期或升级部署后请**重新执行 prepare**。  
- **`voiceId` 仍有用**：表示当前暂存会话已关联的「未入库克隆音色」或复用已有音色 id；`commit` 可选传 `nickname`/`voiceName` 写入 management（均可省略）。若配置 `bypass-voice-recognition=true`，不走 clone 链路时响应里会出现 `"voiceId": null`（仅联调）。

## 5. 接口二：阶段二 commit（含「仅改昵称」）

**URL 唯一**：无论是录音注册后的昵称保存，还是**仅修改昵称**，均为：

`POST /omniasst-meeting/v1/meeting/voiceprint/register/commit`

区别仅在于 Body 是否包含 **`updateNicknameOnly: true`**（见下）。

### 5.1 描述

**常规模式（两阶段注册）**：昵称页保存时调用：根据 **`userId`** 读取 Redis 暂存。声纹流程（含 JSON 新录、multipart `type=1`）：昵称 + 暂存音频转发 management **`voiceprint/register`**。复用流程或 multipart `type=0`/省略 声音流程：仅 **`voice/save`** 更新昵称，**不**调声纹注册。成功后删除该用户暂存。

**仅修改昵称模式**：请求体设置 **`updateNicknameOnly: true`** 时，**不读取 Redis**，也**不要求**先执行 `prepare`。服务端按 `userId` + `provider` 查询已有音色资料，再写入新昵称（音色表 + 声纹展示名）。详见 **§5.5**。

### 5.2 请求

| 项 | 值 |
|----|-----|
| Method | `POST` |
| Path | `/omniasst-meeting/v1/meeting/voiceprint/register/commit` |
| Content-Type | `application/json` |

Body（JSON）：

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| userId | String | 是 | 当前用户 ID；常规模式下须与 prepare 一致（用于定位 Redis 暂存，**无需**再传 `pendingId`） |
| provider | String | 是 | 厂商标识，转发 management `voice/save`；须与 prepare / 已入库音色约定一致，如 `hojo`（恒聚）、`minimax`（MINIMAX） |
| nickname | String | 否 | 展示用昵称；映射为 management 声纹 `userName` / 音色侧 `voiceName`+`nickname`；可省略；非空时长度上限 64 |
| voiceName | String | 否 | 兼容旧参数命名；优先使用 `nickname`；可省略 |
| updateNicknameOnly | Boolean | 否 | **`true`** 时进入 **§5.5 仅改昵称**；不要求 Redis 暂存。默认 `false` 或未传即走常规两阶段提交 |

**说明（常规模式）：** `nickname` 与 `voiceName` 均可省略；均不传时转发 management 的展示名为空字符串（与 management 约定一致）。**勿再传 `replicateType`、`type`**（已由阶段一暂存决定声纹 / 仅声音流程）。非空时昵称长度仍受上限 64 约束。

**说明（`updateNicknameOnly=true`）：** 须至少通过 `nickname` 或 `voiceName` 解析出**非空**昵称（解析规则与常规一致：`nickname` 优先）；**不要**依赖本请求完成声纹注册或克隆，仅更新展示信息。

### 5.3 响应

**成功时：** `resCode` 为 `OK`，`resContent` 为 JSON 对象，常见字段：

| 字段 | 类型 | 说明 |
|------|------|------|
| voiceId | String \| null | 经 clone/save 后的音色 ID；联调 bypass 等未走音色链路时可能为 null |

**成功：** `resCode` 多为 `OK`，**`resMessage` 为 `SUCCESS`**（昵称保存成功弹窗）。

**失败时（会话过期、昵称超长、management save/register 失败等）：** HTTP **200**，**`resCode` 仍为 `OK`**（与统一包装一致），**`resMessage` 为 `SAVE_FAILED`**。**`resContent` 含 `detail` 字段**（原因说明；若异常未携带文案则服务端会给出默认提示），便于 Apifox/联调；亦可查服务端日志。前端可统一按 `SAVE_FAILED` 展示「保存失败 / 再次保存」。

**说明：** 成功与失败在 **`resMessage`** 上区分（`SUCCESS` vs `SAVE_FAILED`），**不要仅用 `resCode` 判断是否保存成功**。

### 5.4 说明

- `commit-skip-management=true` 时**不**调用 management；**与 `updateNicknameOnly=true` 互斥**：仅改昵称必须调用 management，若开启 skip 将返回业务失败（提示无法修改昵称）。  
- **常规模式**：`commit-skip-management=true` 时仅删除 Redis（用于无 management 或联调）。  
- **`provider`**：阶段二调用 management **`voice/save`** 时使用 Body 中的 `provider`，须与 prepare 所选厂商一致，避免与暂存音色渠道不一致。  
- **并发**：同一 `userId` 仅保留**最近一次** `prepare` 的暂存；多设备/多页同时录时以后覆盖先。  
- management 侧接口约定：`POST /omniasst-management/api/v0/voiceprint/register`，`multipart`，参数名 **`userId`、`userName`、`audioFile`**（与 management Controller 一致）。

### 5.5 仅修改昵称（`updateNicknameOnly=true`）

适用于用户**已完成**音色/声纹录入，仅需在会议侧 **同一 `commit` 接口**上改展示昵称的场景。

| 项 | 说明 |
|----|------|
| 前置条件 | 用户在 management 侧**已存在音色资料**（`GET .../v0/voice/profile` 能拿到 `voiceId`）；**无需** `prepare`，**无需** Redis 暂存 |
| 请求体 | `userId`、`provider`、**`updateNicknameOnly`: true**、以及 **`nickname` 或 `voiceName`**（解析后非空，长度 ≤64） |
| 服务端行为 | 1）`GET /v0/voice/profile` 取 `voiceId`、原 `voiceName`；2）`POST /v0/voice/save` 写入新 `nickname`，并保留原音色展示名逻辑；3）`POST /v0/voiceprint/display-name` 更新声纹表 `user_name`；若返回「用户声纹不存在」（用户仅有音色、尚未落声纹行），会议侧**记录日志并视为成功**，不阻断整单 |
| 成功响应 | 与常规 `commit` 相同：`resContent` 含 **`voiceId`**（当前音色 ID） |
| 典型失败 | 未找到音色（无 `voiceId`）、`voice/save` 失败、`display-name` 非「无声纹」类错误、昵称校验失败、`commit-skip-management=true` |

**请求示例：**

```json
{
  "userId": "user_001",
  "provider": "hojo",
  "nickname": "会议展示名",
  "updateNicknameOnly": true
}
```

```bash
curl -X POST "http://{host}:{port}/omniasst-meeting/v1/meeting/voiceprint/register/commit" \
  -H "Content-Type: application/json" \
  -d "{\"userId\":\"user_001\",\"provider\":\"hojo\",\"nickname\":\"会议展示名\",\"updateNicknameOnly\":true}"
```

## 6. 配置项（会议服务）

| 配置键 | 默认值 | 说明 |
|--------|--------|------|
| meeting.voiceprint.register.pending-ttl-minutes | 30 | Redis 暂存过期时间（分钟） |

可在 `application.properties` 或各 profile 中覆盖。

## 7. 调用顺序示例

**分阶段调用（前端仅这两步）：**

```text
1. POST .../prepare   multipart: userId + file + needSave + provider [+ type + voiceName]（或 JSON：userId + audio / audioBase64 [+ type 复用等]）
   → 服务端按 userId 写入 Redis；可选关注 resContent.voiceId

2. POST .../commit    { "userId": "u1", "provider": "hojo" }（可选再加 `nickname` / `voiceName`）
   → 与 prepare 相同 userId 即可提交；成功则声纹在 management 侧 register 流程中落库（未 skip 时）
```

仅改昵称（无需步骤 1）：

```text
POST .../commit    { "userId": "u1", "provider": "hojo", "nickname": "新昵称", "updateNicknameOnly": true }
```
